# DoorMes 原型升级与迁移计划

文档版本：0.4.15  
状态：规划已确认，正在按冻结基线分组实施  
原型仓库：`../luck_door`  
正式项目仓库：`../DoorMes`

目标客户：智宬轩系统门窗。产品模板范围、官网资料基线、模拟/投产边界及客户驱动顺序见[目标客户与产品模板范围](./customer-target-zcsung.md)。

## 1. 迁移目标

将 `luck_door` 原型升级为可维护、可扩展、可审计的正式 DoorMes 项目，并满足以下不可降低的目标：

1. 原型中已有的界面、操作流程、2D绘图、3D展现、联动、BOM和导入导出能力必须完整迁移。
2. 迁移前先固化原型基线和功能一致性矩阵；重构不得造成静默功能退化。
3. 设计领域模型是唯一事实源，2D、3D、BOM和工艺都从同一设计对象图派生。
4. 绘图构件必须具有稳定对象ID和制造语义，支持物资编码、设计构件、制造特征、生产实例和加工工序之间的双向追溯。
5. 桌面、平板、手机复用同一领域命令与计算规则；移动端不是只读缩略版。
6. 发现的原型缺陷或不合理设计全部进入审计记录，不借重构之名静默修改业务结果。

## 2. 一致性定义

### 2.1 必须严格一致的内容

- 功能入口、业务字段、命令结果和状态变化。
- 设计JSON、对象ID、几何尺寸、拓扑和装配关系。
- 2D/3D对象选择、显隐、开合及联动结果。
- BOM、下料、制造特征和工艺计算结果。
- 导入、导出、保存、恢复、确认和冻结语义。
- 同一设计在桌面端与移动端生成的领域数据和计算结果。

双扇业务属性和工艺说明可使用“主动扇/从动扇”，表示先操作并带主锁闭功能的扇与配合关闭的扇；不得使用容易被理解为两个窗体的“主窗/从窗”或含义不完整的“主扇/从扇”。产品2D图不绘制主动/从动或独立扇角色文字，只用开向图示、角度、尺寸和五金表达；兼容数据中的`primary/secondary`继续作为内部枚举保留。

### 2.2 允许自适应的内容

- 手机和平板可将桌面三栏布局重排为抽屉、底部面板或全屏步骤。
- 鼠标右键、悬停、滚轮和双击必须提供可发现的触控等价操作。
- 3D可根据移动设备性能降低抗锯齿、像素比和非关键视觉效果，但不得减少构件或改变几何。

## 3. 目标架构

```text
Design Graph（唯一事实源）
    ├── Geometry / Topology
    ├── Appearance / Component Asset Snapshot
    ├── Manufacturing Feature Extractor
    │       └── Versioned Rule Engine
    │              ├── EBOM
    │              ├── MBOM
    │              ├── Cutting Requirements
    │              ├── Process Routing
    │              └── Production Material Instances
    ├── SVG Renderer
    ├── Three.js Renderer
    └── Shared Application Commands
            ├── Desktop Interaction + Desktop Layout Shell
            └── Touch Interaction + Mobile Layout Shell
```

PC端与移动端采用两个独立布局壳，但不是两套业务前端：

- `DesktopLayoutShell` 组织桌面三栏、鼠标、键盘、右键和快捷键。
- `MobileLayoutShell` 组织手机/平板全屏画布、抽屉、底栏和触控手势。
- 两个壳只负责布局、导航、输入翻译和临时UI状态。
- 领域模型、构件定义、几何拓扑、SVG/Three.js场景生成、应用命令、校验、BOM和工艺算法必须复用同一实现。
- 禁止在共享核心中用 `isMobile` 分叉业务规则；端差异必须终止在布局壳或输入适配器边界。

## 4. 技术决策

| 能力 | 选择 | 约束 |
| --- | --- | --- |
| 2D工程绘图 | 原生SVG，可选SVG.js薄封装 | SVG节点不是领域对象，不参与BOM计算 |
| 3D展现 | Three.js | 通过渲染适配器隔离，不从Mesh反算业务数据 |
| 材质与构件资产 | 版本化外观快照 + 参数化模型/GLB目录 | 外观、物资、型号、资产分层；PC/移动LOD不得改变尺寸、碰撞或BOM |
| 复杂Canvas交互 | Konva仅作为后续候选 | 必须先用性能数据证明需要引入 |
| CAD实体内核 | OpenCascade.js后续可选 | 不进入首轮严格一致性迁移关键路径 |
| 输入事件 | Pointer Events统一鼠标、触控笔、手指 | 禁止在业务层分别维护桌面/移动逻辑 |
| 多端布局 | PC与移动端独立布局壳 | 壳只编排共享组件和命令，不复制领域及算法代码 |
| BOM | 旧算法兼容包装 + 新算法分组迁移 | 新旧引擎双跑，差异必须审核 |
| 生产追溯 | 物资编码 + 稳定对象ID + 制造特征ID + 生产号 | 离散件逐件编号；连续耗材按批；确认冻结后不得重排 |

## 5. 迁移阶段

| 阶段 | 内容 | 主要交付物 |
| --- | --- | --- |
| M0 | 原型冻结、运行方式和数据样本归档 | 基线版本、截图、设计JSON、BOM样本 |
| M1 | 功能和界面一致性盘点 | 桌面/移动一致性矩阵 |
| M2 | 正式工程骨架和质量门禁 | TypeScript工程、测试、格式与构建流程 |
| M3 | 契约、领域模型和设计对象图 | Schema、领域对象、稳定ID、命令接口 |
| M4 | SVG渲染与桌面交互迁移 | 2D严格一致性测试 |
| M5 | 移动布局壳与触控交互 | 独立移动布局、共享核心、平板/手机验收 |
| M6 | Three.js渲染与跨视图联动 | 2D/3D选择、显隐、开合一致性 |
| M7 | 制造特征与BOM算法重构 | EBOM、MBOM、工艺、逐件/逐批生产实例、全链路追溯 |
| M8 | 持久化、版本、确认与冻结 | 兼容导入、不可变BOM快照 |
| M9 | 后端集成与安全审计 | API、权限、审计、异常处理 |
| M10 | 全量回归和发布验收 | 桌面/移动验收报告、差异清零 |

M4、M5和M6可在M3接口稳定后并行推进，但不得各自复制领域或计算逻辑。M7先接入兼容算法，再逐组替换为制造特征驱动的新算法。

## 6. 代码注释与变更记录要求

正式代码的公开对象、函数、算法入口、领域规则和复杂交互控制器必须使用统一TSDoc/Javadoc，至少说明：

- 对象或函数的业务作用。
- 输入、输出、不变量和异常条件。
- 调用流程和关键算法说明。
- 至少一个典型调用或业务示例。
- `@since`版本。
- `@modified`修改日期、版本和变更摘要。
- BOM与工艺规则必须额外记录规则编号和版本来源。

注释用于解释设计意图和业务约束，不重复逐行翻译代码。版本历史同时进入仓库变更日志，避免只依赖注释追踪。

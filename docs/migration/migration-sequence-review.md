# 原型功能对照与迁移顺序审计

文档版本：1.3.2  
日期：2026-09-20  
状态：已评审，按功能优先原则作为后续开发顺序依据

## 1. 评审结论

现有正式工程的包边界、稳定对象ID、命令栈、共享SVG/Three.js投影和制造特征方向正确，不需要推倒重来；但当前计划把“开启类型结构”“运行时开合状态”“3D动画”“2D开启投影”和“后续推拉机构”混在同一个 `UI-3D-003` 大任务中。如果直接进入普通推拉，平开、上悬、推拉会各自形成一套开度状态与控制逻辑，迁移提升推拉、PSK、入墙、转角和折叠时必然再次重构。

因此调整为：先冻结原型开合交互基线，建立共享运动内核和独立预览状态，再回接已经实现的内开内倒、双扇和上悬窗。2026-09-17新增的全构件材质/颜色及五金型号/自定义模型要求会影响所有后续构件，必须在普通推拉前建立外观和资产契约并替换当前硬编码基础；否则推拉、折叠和辅件会复制另一套临时材质与Box模型。此调整不改变已经冻结的BOM结果，只修正依赖顺序。

2026-09-18再次确认执行边界：现阶段专注用户功能，包括界面、绘制、2D/3D、移动交互、材质模型、BOM和工艺。账号登录、组织租户、用户权限角色、审批流、操作审计和生产部署适配统一后置；既有契约仅作为接口预留，不得成为任何当前纵向功能切片的前置依赖。迁移过程中的缺陷记录仍继续维护，但它不是面向终端用户的“操作审计功能”。

2026-09-20全局复盘确认共享运动、真实模型、本地恢复和首条生产表面映射已经形成稳定基础。普通推拉前仍有两个必须关闭的返工风险：画布命中/手势意图尚未统一，以及业务目录项到渲染/模型/生产映射尚未形成完整功能分层。因此执行顺序固定为`UI-2D-007 → APPEAR-004/BOM-009/CAT-001 → CAT-003 → CAT-002 → OPEN-001`。其中UI-2D-007已于0.10.28完成，当前进入生产映射和目录核心；安装编辑和工程节点移到入墙/转角机构的真实前置阶段，不再阻塞普通推拉。

## 4. 当前计划中会导致返工的问题

### 4.1 设计状态与预览状态耦合

正式领域中的 `openingAssembly.openPercent`目前既像设计参数，又直接决定Three.js当前姿态。原型实际上有两层数据：装配设置中的目标开启幅度，以及3D预览中每个活动构件独立变化的当前开度。若继续共用一个字段，拖动3D滑块会产生以下错误选择：

- 修改设计文档、进入撤销栈并让BOM失效；或
- 绕过命令直接改模型，破坏单向数据流；或
- 只能让所有扇同步到同一开度，无法表达双扇顺序和多轨活动扇。

处理原则：保留可持久化的配置开度以兼容原型JSON，但新增独立 `OpeningPreviewState` 保存每个活动构件的即时进度、运动模式、选择和播放状态。预览状态不得使设计变脏、不得触发BOM重算。

### 4.2 渲染器自行计算运动

当前Three.js直接根据开启类型设置旋转，SVG也各自画开启符号。继续加入推拉会把机构判断复制到SVG、Three.js、俯视图和碰撞检查四处。

处理原则：新增纯函数运动求解器，输入静态机构定义和运行进度，输出统一的 `OpeningPoseSnapshot`、轨迹及包络。SVG、Three.js、俯视图、碰撞诊断只消费结果，不自行重算运动规则。

### 4.3 机构模型是重复字段集合

现有内开内倒与上悬接口复制了大量相同字段，并把部分原型占位字段带入正式模型。若按这种方式继续增加12种类型，会形成庞大的重复联合类型和条件分支。

处理原则：抽取只包含稳定公共语义的 `OpeningAssemblyBase`、`OpeningPanel`、轨道/铰接/顺序约束；每种机构使用判别联合保存自身必需参数，不建立一个包含所有可选字段的“万能对象”。旧字段只在兼容适配器中出现。

### 4.4 验收节点粒度过大

此前“上悬3D验收”和“双扇3D验收”只证明了构件结构及固定姿态，没有证明开关、滑块、播放和顺序控制。继续标记为完成会让后续计划误判依赖。

处理原则：把验收拆成“结构/制造映射”和“运行时运动交互”两类。前者保留完成，后者统一进入新的运动内核关卡。

## 5. 稳定目标架构

```text
DesignDocument（持久化设计）
  ├─ Window/Region/OpeningAssembly/Panel/Track/Hardware
  ├─ configuredOpenPercent（兼容原型的设计配置）
  └─ 进入Schema、撤销、保存、BOM

OpeningKinematicsResolver（纯函数共享内核）
  ├─ 机构策略：转轴、线性、多阶段、折叠链
  ├─ 顺序/互锁/极限/碰撞接口
  └─ 输出 MotionDefinition + closed pose

OpeningPreviewStore（临时展现状态）
  ├─ panelId -> progress/motionMode
  ├─ selectedPanelIds/playback/status
  └─ 不进入BOM，不使设计变脏

OpeningMotionController
  ├─ 开启/关闭选中、全部开关、拖动、播放
  ├─ 顺序开启、反序关闭、独立扇例外
  └─ 输出 OpeningPoseSnapshot

Geometry Projection
  ├─ SVG立面/开启图层/俯视轨迹
  ├─ Three.js构件变换与五金宿主
  └─ 运动包络/碰撞诊断

Manufacturing
  └─ 只读取DesignDocument和制造特征，不读取PreviewStore
```

建议新增独立 `opening-kinematics` 包，保持无DOM、无Three.js、无BOM依赖；预览状态与控制器放入 `interaction-core`。渲染器不得反向依赖UI组件。

## 6. 调整后的开发顺序

### 阶段K0：冻结原型运动基线

1. 为单扇平开、内开内倒、双扇飞梃、双扇固定中梃、上悬和下悬保存设计夹具。
2. 固化原型3D交互脚本：构件选择、多选、0/50/100%、选中/全部开关、播放和反序关闭。
3. 固化2D“开启状态”开关、立面和俯视投影快照。
4. 明确 `openPercent` 的设计配置语义与预览即时进度语义。

完成门：交互、JSON、几何和BOM预期均有独立基线，不能只保存截图。

### 阶段K1：运动内核和状态边界

1. 抽取公共装配/面板契约和机构判别联合。
2. 建立 `OpeningPreviewStore`，证明预览变化不增加设计revision、不进入撤销栈、不改变BOM哈希。
3. 建立机构策略注册表、姿态快照、分阶段运动和顺序约束接口。
4. 建立扇侧五金随运动宿主、框侧五金保持静止的统一映射。

完成门：无可见行为变化，现有68项测试和七组BOM夹具继续完全一致；新增状态隔离和纯运动函数测试。

### 阶段K2：回接现有转轴机构

1. 内开内倒单扇、双扇飞梃、双扇固定中梃和上悬全部改为消费姿态快照。
2. 补侧平开、下悬和门扇，复用通用转轴策略但保留各自业务类型与五金规则。
3. 接入选中/全部开关、滑块、播放、顺序开/反序关和内倒/平开模式切换。
4. 2D增加“开启状态”图层，并与俯视投影共用同一姿态。
5. PC控制条与移动抽屉只发送相同预览意图。

完成门：PC和390×844移动端真实操作通过；固定中梃两扇可独立，飞梃遵守主动/从动顺序，上悬保持顶部铰接；BOM完全不随预览开度变化。

### 阶段K2.5：材质外观与五金模型基础

1. 定义版本化外观快照，覆盖墙、框、扇、中梃/飞梃、玻璃、包边和五金，并区分室内、室外和侧边表面。
2. 分离物资编码、外观预设、构件型号和纹理/GLB资产；明确哪些选择只改变展示，哪些需要BOM/表面工艺重算。
3. 建立共享AppearanceResolver与材质缓存，统一SVG降级表现、Three PBR材质和GPU资源释放。
4. 建立五金型号目录，保存实际毫米尺寸、参数化/GLB形状、安装枢轴/方向、LOD、fallback、物资和加工模板；先替换现有执手、合页、锁点/锁座等通用Box。
5. 自定义模型经过单位、轴向、包围盒、面数、纹理、安全、内容哈希和版本发布校验；PC/移动提交相同命令。

完成门：至少三种锁具型号和一个受控自定义模型在2D/3D、开合宿主、选择、碰撞、BOM与工艺中一致；移动LOD不得改变业务尺寸或结果。详细方案见`appearance-and-component-assets.md`。

### 阶段K3：普通推拉纵向切片

1. 建立2–6扇、1–5活动扇、2–4轨的静态模型和稳定面板/轨道ID。
2. 在线性运动策略中实现左右/双向收拢、活动扇选择和轨道约束。
3. 同步2D立面、俯视轨迹、3D滑动、对象树、PC/移动控制、BOM和工艺。
4. 冻结原型夹具并逐字段双跑。

完成门：这才是“基础推拉完成”，不得只完成一个固定3D姿态。

### 阶段K4：多阶段推拉

按依赖顺序迁移：提升推拉 → 平行推拉 → PSK。三者复用普通推拉轨道和面板结构，只增加“提升/脱离密封面/内倒”等阶段，不复制控制器。

完成门：阶段切换、运动顺序、专用五金、2D/3D和BOM一致。

### 阶段K5：安装空间相关机构

1. 先建立墙洞、框位、包套和空间碰撞接口。
2. 再迁入墙推拉、转角推拉和上下提拉。
3. 入墙行程受墙腔约束，转角行程受两翼轨道/转角节点约束。

完成门：活动构件不得穿墙、穿柱或越轨；安装和组合BOM来源唯一。

### 阶段K6：折叠与纱窗

1. 迁2–12扇折叠链、通行扇和奇偶扇顺序。
2. 建立固定、平开、推拉和卷轴纱窗的独立构件/运动/BOM。
3. 增加主窗扇与纱窗的互锁和碰撞接口。

完成门：多构件顺序、折叠链姿态和制造规则可追溯。

### 阶段G：其余图形与工程能力

1. `Infill`模型：百叶、格条、面板、留空、防盗条和玻璃护栏。
2. Annotation模型：文字、圆孔、方孔和锁具标记，与正式加工特征严格分离。
3. 统一轮廓接口后迁拱形、梯形、缺角和DIY异形。
4. 迁拼接/转角节点、多窗组合、包套施工详图及完整安装BOM。
5. 领域Schema稳定后迁项目、组件库、材料库、保存/恢复和BOM确认冻结；先完成功能，再把本地实现替换为正式后端。
6. 全部核心功能及多端一致性验收后，最后接账号、权限、审批、操作审计和生产部署治理。

## 7. 每个纵向切片的强制完成标准

任何新构件或开启机构必须一次性交付下列内容，不再接受“先画出来、后补算法”的半切片：

1. 原型入口、操作脚本、截图、设计JSON和BOM夹具。
2. 类型化领域对象、稳定ID、Schema校验和旧数据适配。
3. 共享命令或预览意图、撤销边界及错误诊断。
4. 2D立面、尺寸、俯视/轨迹及选择高亮。
5. 3D闭合姿态、全开姿态、中间姿态、运动宿主和资源释放。
6. PC与移动端等价入口，核心只实现一次。
7. EBOM、MBOM、汇总、下料、工艺和生产确认边界。
8. 单元测试、原型双跑、浏览器操作、控制台和视觉验收。
9. 审计差异、供应商缺失数据和明确后续TODO。

## 8. 禁止性约束

- 禁止在SVG和Three.js中分别实现同一种机构的运动公式。
- 禁止把预览开度写入BOM输入或因播放动画使设计变脏。
- 禁止为移动端复制领域、运动、渲染或算料规则。
- 禁止用一个包含全部可选字段的万能Opening对象承载所有机构。
- 禁止先迁入墙/转角推拉再补墙洞和工程节点模型。
- 禁止把文字/装饰孔位直接当成可下发MES的加工特征。
- 禁止在领域Schema尚未稳定时固定后端表结构或组件库存储格式。

# 型材表面生产映射与BOM失效传播

文档版本：0.1.0  
对应版本：DoorMes 0.10.24  
状态：首条纵向链路完成，APPEAR-004/BOM-009继续实施

## 1. 本次交付边界

本次只把已经具备可靠业务边界的“型材表面处理”接入制造，不把所有外观字段直接解释为物资：

| 设计选择 | 是否影响制造 | 当前结果 |
| --- | --- | --- |
| 颜色、RAL显示值、金属度、粗糙度、透明度、纹理、UV | 否 | 只影响SVG/Three；BOM状态保持`current` |
| 普通`finishCode` | 否 | 继续作为显示/说明字段，计算层不读取 |
| 目录批准的框/扇/中梃/飞梃内外侧/边面处理 | 是 | 生成`surface-treatment`工艺特征 |
| 预览或手工修改的生产映射 | 否 | 不生成工艺，不得沿用旧目录生产身份 |
| 墙体外观 | 否 | 现场宿主不进入门窗产品BOM |
| 玻璃规格/SKU、包边材料 | 尚未完成 | 保留在APPEAR-004后续TODO |

## 2. 生产映射契约

`VisualAppearanceSnapshot.productionMapping`与`finishCode`明确分离。只有以下完整快照可以进入计算：

```ts
{
  schemaVersion: "doormes-surface-production.v1",
  productionStatus: "catalog-approved",
  treatmentCode: "ST-POWDER-RAL7016",
  processTemplateId: "PROC-POWDER-AL-V1"
}
```

归一化算法要求目录批准状态同时具有处理编码和版本化工艺模板；缺任一字段即拒绝项目导入、历史恢复或正式命令。手工编辑器重新构造外观草稿，不复制目录生产映射，因此改变颜色/纹理后必须重新选择已批准目录项。

## 3. 工艺提取算法

1. 正式BOM仍先生成框、扇、中梃、飞梃等`profile-cut`制造特征。
2. 计算层按稳定`sourceComponentId`把型材归类到四个语义角色；飞梃优先于一般中梃判断，避免错误归属。
3. 对每个角色的`inside/outside/edge`逐面检查显式生产映射。
4. 只有`catalog-approved`映射生成`surface-treatment`。
5. 工艺特征引用全部受影响的型材特征ID，并以`Σ(毛料长度 × 下单数量)`计算处理总长和米数。
6. 处理工艺不替换底层型材物资编码，因此旧MBOM、采购汇总和下料数量保持逐字段兼容。

## 4. BOM新鲜度状态

共享`FormalBomCalculationStore`维护三个状态：

- `not-calculated`：当前设计尚无正式计算结果；
- `current`：当前制造输入与最后计算输入完全一致；
- `stale`：尺寸、拓扑、开启构造、安装、目录、批准表面处理或型号制造参数已变化。

制造输入指纹使用完整规范JSON而不是短哈希，避免碰撞导致错误的“仍为当前”判断。指纹会规范化旧窗的默认视觉配置，只保留计算实际消费的表面生产映射和五金型号/尺寸/安装/物资/加工字段；纯渲染字段被排除。撤销回已计算输入后，状态无需制造新快照即可恢复`current`。

## 5. 自动验证

- 目录批准的RAL7016外框室外面生成一条工艺特征并引用四段框料；
- 工艺总长严格等于四段框料毛长乘订单数量之和；
- 新增工艺前后`features`、MBOM和汇总BOM逐字段一致；
- 不完整的批准映射被领域归一化拒绝；
- 手工修改型材颜色、粗糙度和`finishCode`后BOM仍为`current`；
- 选择批准表面处理后变为`stale`，重算后变为`current`；
- 撤销/重做在`current/stale`间确定性恢复；
- 19个测试文件173项、冻结原型BOM重放和生产构建通过。

本阶段按用户要求未执行浏览器自动操作；2D/3D视觉仍由用户人工验收。
